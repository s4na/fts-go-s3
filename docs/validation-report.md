# S3 上の全文検索プロトタイプ: 検証結果

Issue [#3](https://github.com/s4na/fts-go-s3/issues/3) の検証結果を記録する。以下は GitHub Actions 上の単一実行であり、実 S3 や本番負荷での SLA・料金の測定ではない。転送量は HTTP ボディの実測で、ヘッダーやプロトコルのオーバーヘッドを含まない。Wikipedia の固定リビジョンと青空文庫を使い、文書・クエリに NFKC と小文字化を適用した部分文字列検索をオラクルとした。

## 成立性

| 規模と条件 | 正しさ | 構築 | 検索 |
|---|---|---|---|
| M: 10,002 文書、256シャード、両ストレージ、upstream 50ms | 178クエリで取りこぼし0件 | — | マニフェストキャッシュあり784 GET、受信130,574,002バイト、p95 VersityGW 469ms / SeaweedFS 486ms |
| L: 100,002 文書、256シャード、SeaweedFS、遅延なし | 178クエリで取りこぼし0件、誤候補263,658件 | 134,384ms、258 PUT、送信277,566,923バイト | キャッシュなし962 GET・受信1,190,234,830バイト、あり784 GET・受信862,674,958バイト |

[M の遅延実験](https://github.com/s4na/fts-go-s3/actions/runs/41012211449)と [L の実行](https://github.com/s4na/fts-go-s3/actions/runs/41012488585)を参照。GET・バイト数は178クエリの合計であり、PUTにはバケット作成を含む。Toxiproxy の遅延は TCP の upstream データ単位に作用するため、HTTP リクエストごとに厳密に50msを加えるものではない。L の候補は1,836,135件で、誤候補率は約14.4%だった。

このデータとクエリでは必要部分の読み出しと取りこぼしゼロを確認でき、暫定の M・50ms・キャッシュあり p95 1秒以内も満たした。一方、L のキャッシュなし受信は1クエリ平均約6.7 MBであり、ネットワーク転送量・料金は未解決である。S3、R2など実サービスの料金や距離・並列性は測定していない。

## 1ページ更新と劣化

[反復更新](https://github.com/s4na/fts-go-s3/actions/runs/41014263592)では、100記事を対象に個別更新1,000回と100件バッチ10回を両ストレージで実行した。個別更新は合計16,200 PUT・送信58,335,217バイト、バッチは合計170 PUT・送信12,838,460バイト。検査した4クエリの各時点で取りこぼしと削除済み候補は0件だった。16シャードなので個別更新の PUT は文書数に比例せず上限があるが、マニフェストは全ドキュメントの版を含むため、書き込みバイトは文書数・更新履歴に応じて増える。

圧縮前の961セグメントでは4クエリに5,769 GETが必要だった。1セグメントに統合すると10 GETに戻ったが、圧縮そのものに15,377 GET・17 PUTを要した。これは100記事・16シャードでの値であり、大規模での更新費用を推定するには追加計測が必要である。

[圧縮方針の比較](https://github.com/s4na/fts-go-s3/actions/runs/41015483320)では、個別更新100回ごとに圧縮すると、その直後の4クエリは10 GETとなった。途中10回の圧縮だけで15,370 GET・170 PUTを使い、最後にさらに177 GET・17 PUTが必要だった。最後に一度だけ統合した場合は15,377 GET・17 PUTだった。頻繁な圧縮は検索劣化を抑える一方、PUTとマニフェストの更新量を増やす。

条件付きマニフェスト更新では、同じ ETag を読んだ2ライターの片方を競合として拒否し、再試行後に両方の変更が見えることを確認した。旧スナップショットの保護と猶予後の回収も[両ストレージで検証](https://github.com/s4na/fts-go-s3/actions/runs/41014940376)した。ただし、回収の試作は読み取り時間・時計差・ストレージ処理時間の上限を仮定し、未公開の孤立オブジェクトは回収しない。この前提を実環境で保証できるかは未検証である。

## 設計判断の影響

- [シャード比較](https://github.com/s4na/fts-go-s3/actions/runs/41012670705): S・256シャードで単一オブジェクトの Range GET と分割方式は、178クエリ・キャッシュありの受信がともに19,888,413バイト、784 GET、取りこぼし0件だった。構築はバケット作成を含め Range 3 PUT、分割258 PUT。Range の目次によりキャッシュなし受信は24,384,159バイト、分割は22,835,025バイトだった。
- [4,096シャードの途中結果](https://github.com/s4na/fts-go-s3/actions/runs/41015409254): VersityGW・Sでは構築4,098 PUT、キャッシュあり検索791 GET・受信1,474,182バイト・取りこぼし0件だった。256シャードでは構築258 PUT・受信19,888,413バイトだった。キャッシュのリース導入前後でGETの計数が異なるため、厳密な同条件の比較は同一実行の全条件を参照する。
- [Bloom フィルタ比較](https://github.com/s4na/fts-go-s3/actions/runs/41012962428): M・単一セグメントではフィルタによる GET 削減は962から961回にとどまり、キャッシュなし受信は161,435,286から448,761,813バイトへ増えた。この配置では大きなフィルタをマニフェストに含めるコストが支配的だった。セグメント数が多い場合は別途評価が必要である。
- [符号化比較](https://github.com/s4na/fts-go-s3/actions/runs/41015135868): M の178クエリ由来、479 term・1,062,862ポスティングで差分 varint は1,065,261バイト、Roaring は1,700,000バイト。どちらも復号一致を確認した。これは選んだクエリ集合の値であり、全 term や更新・積集合の速度を網羅しない。

## 依存と bleve

| 候補 | この検証での扱い | 理由 |
|---|---|---|
| `golang.org/x/text` | 本体で採用 | Unicode の NFKC データを自前で維持しない。直接依存1件。 |
| Roaring Bitmap | 比較用の別モジュール、本体では未採用 | 上記クエリの符号化サイズは varint の方が小さかった。別モジュールには bitset、smat、x/sys の間接依存が入る。 |
| AWS SDK for Go v2 | 比較用の別モジュール | [両ストレージ](https://github.com/s4na/fts-go-s3/actions/runs/41013478781)で基本操作と条件付き PUT が通った。SDK専用バイナリ11,897,262バイト、自作専用8,801,713バイト（[比較](https://github.com/s4na/fts-go-s3/actions/runs/41014250453)）。SDK関連のモジュールグラフは11モジュール、自作クライアントと計測コードは239行。対応範囲・堅牢性が異なるため、行数やサイズだけでは優劣を決められない。 |
| bleve | 比較用の別モジュール | 既定 MatchQuery は部分文字列検索と意味が異なり、同じオラクルに対する候補品質をそのまま代替できなかった。 |

[bleve の M 結果](https://github.com/s4na/fts-go-s3/actions/runs/41013813711)は10,002文書・178クエリで構築40,670ms、索引1,083,474,776バイト、p95 9ms、オラクルとの差は取りこぼし43,405件・誤候補1,194,441件だった。[L](https://github.com/s4na/fts-go-s3/actions/runs/41014959896)では100,002文書、構築259,419ms、索引6,628,213,001バイト、p95 161ms、取りこぼし343,408件だった。既定アナライザと MatchQuery を使った仕様差を含み、bleve 自体の欠陥の証明ではない。過去の実装や失敗時のログはこの検証に含まれておらず、当時の失敗原因を特定したとは言えない。今後は検索仕様を明示し、同じオラクル・データ・計測を先に用意する。

比較用モジュールの `go list -m all` では、比較プログラム自身と置換した本体モジュールを除くグラフのモジュール数は Roaring 14、SDK 12、bleve 52だった。これらにはビルド時に使われないテスト・ツール由来のモジュールや本体の `x/text` も含まれ、実際のバイナリにリンクされた依存数とは異なる。詳細は各 artifact のモジュール一覧と `go mod graph` を参照する。

## 次の判断

A2 は今回の限定条件では検索と差分更新を実現できたが、GET と転送量の増大、頻繁な圧縮コスト、マニフェストの肥大、回収の時間・時計前提が残る。現時点では本番採用を決めず、想定文書数、更新頻度、ストレージ単価、許容遅延を決めたうえで A1 または A4 と同じ負荷・オラクルで比較することを推奨する。既定 bleve の数字をそのまま A2 と同じ検索仕様の比較値とは扱わない。
