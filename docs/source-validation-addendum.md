# S3 原本文書と圧縮中検索の追加検証

既存の [検証報告](validation-report.md) に加え、原本文書を S3 オブジェクトとして扱う経路と、検索中の圧縮を検証した。実行は GitHub Actions 上の VersityGW と SeaweedFS を使用している。

## 原本文書の保存と更新

[実行結果](https://github.com/s4na/fts-go-s3/actions/runs/41018393323)では、S（1,002 文書）と M（10,002 文書）について、各文書を個別に保存し、一覧のページ送りと全件の読み戻し・内容一致を確認した。その文書から索引を作り、文書と索引の更新、別文書の追加・検索・削除も確認した。両ストレージ、両規模の各 4 クエリで偽陰性は 0 件だった。

M の両ストレージで原文の保存は 10,002 PUT、一覧と全件読み込みは 11 ページ・10,013 GET、索引構築は 257 PUT だった。1 文書の原文と索引の更新は 2 GET・258 PUT だった。これはこの実装・データ・設定での観測値であり、S3 の実料金ではない。

## 検索と圧縮の同時実行

[実行結果](https://github.com/s4na/fts-go-s3/actions/runs/41018408635)では、旧セグメントの取得を途中で停止した検索に対して圧縮と早すぎる削除の拒否を実行し、その後検索を再開して期待する結果を得た。VersityGW と SeaweedFS の双方で成功した。これは制御した一つの並行実行順序の検証であり、あらゆるタイミングや実際の AWS S3 での動作を保証するものではない。旧セグメント回収の時計差と処理時間の前提は既存の報告を参照。
